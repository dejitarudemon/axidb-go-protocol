# Терминология

`Узел` - самостоятельный участник сетевого общения в рамках настоящего протокола. Узлом может быть клиент или сервер.

`Запрос` - логически обособленное сообщение согласно структуре кадра и формата конкретной версии, которое выполняется узлом, в рамках логического выполнения операции.

Запрос может быть:
- `инициирующим` - первым в структуре запрос-ответ.
- `ответным` - вторым в структуре запрос-ответ.

`Кадр` - обобщенная структура, содержащая данные, достаточные для корректной передачи запроса.

# Основная структура кадра

```text
| Magic bytes (2 bytes) | Version (1 byte) | Headers | Body | Checksum (4 bytes) |
```

Где:

- `Magic bytes` - уникальная последовательность, обозначающая, что настоящий кадр относится к протоколу AxiDB (0A DB).
- `Version` - версия протокола (от 0 до 255).
- `Headers` - различные служебные данные/флаги, определяемые версией протокола (далее может упоминаться как заголовки).
- `Body` - основные данные сообщения.
- `Checksum` - контрольная сумма кадра. Конкретные реализации сами определяют, что именно покрывает контрольная сумма.

Для **всех** полей, сообщений и т.п. используется Big Endian способ записи байтов в сообщениях по умолчанию.

# Установление общей версии

Вне зависимости от протокола и способа его реализации, любое подключение должно осуществляться со служебного кадра версии 0 (далее Hello-запрос) согласно следующему формату:

```text
| 0A DB | 00 | Version Len (1 byte) | Version 1 | Version 2 | ...  | Version N | CheckSum |
```

Где:

- `Version Len` - кол-во поддерживаемых версий протокола узлом.
- `Version N` - конкретная поддерживая версия.

В основном формате кадра Headers представлен одним Version Len. Versions представлены как Body.

Для Checksum используется алгоритм `CRC32/XFER`. Checksum покрывает Version Len и Version N.

**Примечание автора**: дублирование версий допускается, но крайне нежелательно. При дубле версий узел должен игнорировать их.

## Алгоритм установления соединения

1. Клиент устанавливает TCP-соединение с сервером (дополнительно TLS или иное шифрование сетевого трафика, опционально. Зависит от конкретной реализации сервера).
2. Клиент отправляет Hello-запрос, указывая поддерживаемые версии.
3. Сервер отвечает сообщением с таким же форматом со своими поддерживаемыми версиями.
4. Клиент запоминает версии, поддерживаемую и клиентом, и сервером.
5. Клиент и сервер действуют дальше согласно версии протокола.

Если клиент не поддерживает ни одну версию, которую поддерживает сервер, соединение не может быть установлено, клиент должен разорвать соединение, в противном случае, сервер разорвет его через некоторое конечное время.

Примеры Hello-запросов от клиента к серверу и обратно:

```text
Клиент -> Сервер

Hex-версия:

0A DB 00 03 01 02 03 EC 29 CA C3

Расшифровка:
	Version: 0 (Hello)
	Versions: 1, 2, 3


Сервер -> Клиент

Hex-версия:

0A DB 00 04 01 04 07 0B DB E1 D7 BD

Расшифровка:
	Version: 0 (Hello)
	Versions: 1, 4, 7, 11
```

Если клиент отправляет большее кол-во версий, чем указано в Version Len, сервер разрывает соединение.

### Типы данных

Ниже приведены коды типов данных и форматы их записей. Узлы должны гарантировать, что данные соответствуют требованиям указанных типов данных.

#### Последовательность байт

Код: 0

Пример: 0A 12 33 45

Особенности: -

Проверка соответствия:
1. Реальная длина соответствует заявленной.

Формат записи:

```text
| Value Len (4 bytes) | Value |
```

Где:

- `Value Len` - длина байтовой последовательности.
- `Value` - байтовая последовательность.

Алгоритм кодирования:
1. Внести длину байтовой последовательности.
2. Внести байтовую последовательность.

Алгоритм декодирования:
1. Прочитать первые 4 байта - Value Len.
2. Прочитать следующие Value Len байт.

Пример кодирования-декодирования:

```text
Hex-версия: 00 00 00 04 0A 12 33 45

Расшифровка:
	Value Len: 4
	Value: 0A 12 33 45
```

#### Типизированный массив

Код: 1

Пример: {1, 2, 3}

Особенности: каждое Value должно быть раскрыто для типов "[Байтовая последовательность](#байтовая-последовательнос)", "[Типизированный массив](#типизированный-массив)", "[Нетипизированный массив](#нетипизированный-массив)", "[Строка](#строка)", "[JSON-документ](#json-документ)" как структура, описанная в каждом указанном типе.

Проверка соответствия:
1. Указанная длина массива соответствует реальной.
2. Каждый элемент соответствует заявленному типу.

Формат записи:

```text
| Array Len (4 bytes) | Value Type (1 byte) | Value 1 | Value 2 | ... | Value N |
```

Где:

- `Array Len `- кол-во элементов.
- `Value Type` - тип элемента массива.
- `Value N` - элементы массива.

Алгоритм кодирования:
1. Внести кол-во элементов в массиве.
2. Внести 1 раз тип элементов.
3. Внести все элементы последовательно, кодируя их согласно их типу.

Алгоритм декодирования:
1. Прочитать первые 4 байта - Array Len.
2. Прочитать 1 байт - Value Type.
3. Декодировать элементы последовательно согласно их алгоритму декодирования, проверяя каждый элемент согласно проверке соответствия его типа.

Пример кодирования-декодирования:

```text
Hex-версия: 00 00 00 02 03 00 00 00 00 00 00 00 01 00 00 00 00 00 00 00

Расшифровка:
	Array Len: 2
	Value Type: int
	Value 1: 1
	Value 2: 2
```

#### Нетипизированный массив

Код: 2

Пример: {1, "hello world", 12.3}

Особенности: каждое Value должно быть раскрыто для типов "[Байтовая последовательность](#байтовая-последовательнос)", "[Типизированный массив](#типизированный-массив)", "[Нетипизированный массив](#нетипизированный-массив)", "[Строка](#строка)", "[JSON-документ](#json-документ)" как структура, описанная в каждом указанном типе.

Проверка соответствия:
1. Указанная длина массива соответствует реальной.
2. Каждый элемент соответствует заявленному типу этого элемента.

Формат записи:

```text
| Array Len (4 bytes) | Value 1 Type (1 byte) | Value 1 | Value 2 Type (1 byte) | Value 2 | ... | Value N |
```

Где:

- `Array Len` - кол-во элементов.
- `Value Type N` - тип элемента массива № N.
- `Value N `- элементы массива.

Алгоритм кодирования:
1. Внести кол-во элементов в массиве.
2. Внести тип элемента.
3. Внести элемент согласно его алгоритму кодирования.
4. Повторить шаги 2-3 до конца элементов.

Алгоритм декодирования:
1. Прочитать первые 4 байта - Array Len.
2. Прочитать 1 байт - Value Type.
3. Декодировать и проверить элемент последовательно согласно их типу. 
4. Повторить шаги 2-3 до конца элементов.

Пример кодирования-декодирования:

```text
Hex-версия: 00 00 00 03 03 00 00 00 00 00 00 00 01 06 00 00 00 0B 68 65 6C 6C 6F 20 77 6F 72 6C 64 05 40 28 99 99 99 99 99 9A

Расшифровка:
	Array Len: 3
	Value 1:
		Value Type: int
		Value: 1
	Value 2:
		Value Type: string
		Value:
			Value Len: 11
			Value: hello world
	Value 3:
		Value Type: float
		Value: 12.3
```

Пример кодирования-декодирования:

```text

Расшифровка:
```

### Ошибки

Ниже приведены коды ошибок и возвращаемые Details.

Примечание: иные коды резервные, и могут быть использованы в частной реализации настоящего протокола, или будут дополняться в настоящей версии.

#### No Hello

Код ошибки: 0

Примеры:
1. Клиент после подключения не прислал Hello-запрос

Причина: несогласование версий, отсутствие Hello-запроса

Особенности: эта ошибка не отправляется клиенту, сохраняется только в логах. Соединение разрывается.

Как исправить: после установления TCP-соединения отправить Hello-запрос.

Структура Details: -

#### Unsupported Version

Код: 1

Примеры:
1. Клиент отправляет кадр версии, которую сервер не поддерживает.

Причина: версия протокола не поддерживается принимающим узлом.

Особенности: эта ошибка должна быть отправлена на последней совместно использованной версии протокола, если такая версия была установлена. Если ошибка появилась до Handshake, узел отправляет сообщение на минимально поддерживаемой собой версии.

Как исправить: перейти на поддерживаемую принимающим узлом версию протокола.

Структура Details: -

#### Unexpected Command

Код: 2

Примеры:
1. Клиент присылает Read на запрос Ping от сервера.

Причина: неожиданная команда. Принимающий узел ожидал другую команду.

Особенности: -

Как исправить: отправить новую команду, которую ожидает принимающий узел.

Структура Details:

```text
| Expected Command (1 byte) |
```

Где:

- `Expected Command` - Ожидаемая команда. Принимает значение от 0 до 255.

#### Unsupported Command

Код: 3

Примеры:
1. Клиент отправил кадр с командой 8.

Причина: неподдерживаемая команда. Указанная команда не принадлежит списку поддерживаемых команд текущей версии.

Особенности: -

Как исправить: использовать команды из текущей версии протокола или перейти на другую версию, где такая команда поддерживается (если такая версия существует и поддерживается клиентом и сервером).

Структура Details:-

#### Requests Conflict

Код: 4

Примеры:
1. Клиент отправляет запрос с Request ID 1 и сразу новый с Request ID 1.

Причина: принят запрос с Request ID, который уже зарегистрирован у узла, который обрабатывает запрос.

Особенности: первый запрос (в порядке времени получения) не прерывается. Второй запрос не обрабатывается (возвращается ошибка). Ответ на первый запрос должен прийти в штатном режиме.

Как исправить: повторить запрос с другим Request ID.

Структура Details: -

#### Unsupported Compression

Код: 5

Примеры:
1. Клиент/сервер использует алгоритм сжатия, не поддерживаемый другим узлом.

Причина: неподдерживаемый алгоритм сжатия. Указанный алгоритм не поддерживается принимающей стороной.

Особенности: нет

Как исправить: отправить запрос с поддерживаемым принимающим узлом алгоритмом.

Структура Details: -

#### Body Limit Is Exceeded

Код: 6

Примеры:
1. Клиент отправил запрос с Body Len = 10 при ограничении сервера на размер сообщения в 8 байт.

Причина: размер Body выше установленного ограничения сервера на размер тела.

Особенности:  возможна десинхронизация.

Как исправить: переподключиться при разрыве соединения, уменьшить размер данных или использовать сжатие.

Структура Details:

```text
| Current Body Size Limit (4 bytes) |
```

Где:

- Current Body Size Limit - текущее ограничение по размеру тела. Принимает значения от 0 до 4294967295.

#### Mismatched CheckSum

Код: 7

Примеры:
1. Клиент прислал запрос с битыми Headers или Body.
2. Клиент прислал запрос с Body Len = 8, хотя реальная длина составляет 9 байт (при лимите сервера на размер Body в 12 байт).

Причина: контрольная сумма Headers и Body не совпадают с заявленной.

Особенности: возможна десинхронизация, если ошибка в Body Len.

Как исправить: переподключиться при разрыве соединения, отправить запрос с корректным Checksum.

Структура Details: -

#### Request Interrupted

Код: 12

Примеры:
1. Сервер выполнял запрос, но его принудительно выключают.
2. Во время выполнения Batch-запроса с флагом "Прерывание при ошибке", установленным в 1, одна из операций не выполнена из-за ошибки. В таком случае ошибка будет выведена в соответствующий Result Body. 

Причина: сервер зарегистрировал запрос, но не может его выполнить из-за прерывания выполнения.

Особенности: -

Как исправить: проверить доступность сервера. в случае батча проверить ошибку, вызвавшую прерывание последующих операций.

Структура Details: -

#### Batch Limit Is Exceeded

Код: 13

Примеры:
1. Клиент отправил Batch-запрос, в который заложил 10 операций, при ограничение сервера в 8 операций в 1 батче.

Причина: значение Requests Len выше ограничения сервера на кол-во операций в 1 батче.

Особенности: -

Как исправить: разделить батч на несколько отделных.

Структура Details:

```text
| Current Batch Size Limit (4 bytes) |
```

Где:

- `Current Batch Size Limit` - текущее ограничение по кол-ву операций в Batch-запросе. Принимает значения от 0 до 4294967295.

#### Unexpected Command In Batch

Код: 14

Примеры:
1. Клиент отправил Batch-запрос, где для запроса с номером 2 указал команду Handshake.

Причина: значение Command одного из Request не является Read, Write, Delete.

Особенности: -

Как исправить: убрать запрос из батча. Отправить отдельно по необходимости.

Структура Details:

```text
| Request Number (4 bytes) |
```

Где:

- `Request Number` - номер запроса с некорректным Command.

#### Invalid Request ID

Код: 15

Примеры:
1. Клиент отправил Handshake-запрос с Request ID = 1.
2. Клиент отправил Read-запрос с Request ID = 0.

Причина: используется RequestID, непредусмотренный для данного запроса.

Особенности: -

Как исправить: сменить Request ID для данного запроса.

Структура Details: -

#### Unauthorized

Код: 16

Примеры:
1. Клиент отправил Handshake-запрос с неверным логином и/или паролем.

Причина: неверный логин и/или пароль в Handshake-запросе.

Особенности: -

Как исправить: ввести корректные логин и пароль.

Структура Details: -

#### Restricted Request

Код: 17

Примеры:
1. Клиент отправил Read-запрос для данных, к которым у него нет доступа.

Причина: для текущего клиента нет доступа к указанной команде и Body.

Особенности: -

Как исправить: сообщить системному администратору или иному лицу, который отвечает за политики прав доступа.

Структура Details: -

#### Unknown Error Code

Код: 18

Примеры:
1. Сервер вернул неизвестную ошибку не из настоящей спецификации.

Причина: код ошибки не из официального списка.

Особенности: -

Как исправить: переотправить запрос с корректным номером ошибки.

Структура Details: -

### Сжатие

Ниже приведен список алгоритмов сжатия и кодов, соответствующих им.

| Код | Алгоритм |
| --- | -------- |
| 0   | -        |
| 1   | zstd     |
| 2   | lz4      |
Иные коды резервные, и могут быть использованы в частной реализации настоящего протокола, или будут дополняться в настоящей версии.

### Headers

```text
| Command (1 byte) | RequestID (4 byte) | Compression (1 byte) | Body Len (4 byte) |
```

Где:

- `Command` - номер команды (см. [Command](#command)).
- `RequestID` - уникальный идентификатор запроса для клиента, Который не обрабатывается узлом в настоящий момент.
- `Compression` - используемое для Body сжатие.
- `Body Len` - длина Body в байтах.

#### Command

Байт, обозначающий номер команды.

Существующие команды:

0. `Handshake` - первый запрос, инициируемый только клиентом после запроса Hello, в котором он передает необходимую информацию для дальнейшей работы: поддерживаемые методы сжатия и т.д. Подробности см. в [Алгоритме рукопожатия](#алгоритм-рукопожатия).
1. `Answer` - ответ на запрос. Не может использоваться как самостоятельный запрос, при ответе на несуществующую запрос должна вернуться ошибка [Unexpected Command](#unexpected-command). Может использоваться и клиентом, и сервером.
2. `Read` - запрос на получение данных. Может использоваться только клиентом. Подробности см. в [Чтение данных]().
3. `Write` - запрос на запись данных. Может использоваться только клиентом. Подробности см. в [Записи данных]().
4. `Delete` - запрос на удаление данных. Может использоваться только клиентом. Подробности см. в [Удалении данных]().
5. `Batch` - множество запросов. Не является транзакцией. Может использоваться только клиентом. Подробности см. в [Батчи и их применение]().
6. `Ping` -  запрос на проверку доступности. Может использоваться и клиентом, и сервером. Подробности см. в [Проверках доступности]().

Иные команды в текущей версии резервные, и могут использоваться конкретными реализациями настоящей версии протокола. В противном случае запросы с резервными командами должны возвращаться с ошибкой [Unsupported Command](#unsupported-command).

#### Request ID

Уникальный для текущего подключения идентификатор от 0 до 4294967295, используемый для асинхронности протокола. 

Значение 0 используется только для Handshake и Answer на Handshake.

#### Compression

Значение от 0 до 255. Используется для обозначения алгоритма, используемого для сжатия Body. 0 обозначает отсутствие сжатия. Список поддерживаемых алгоритмов см. в [Сжатие](#сжатие).

#### Body Len

Значение от 0 до 4294967295 (4 ГиБ). Используется для обозначения размера Body (после сжатия, если оно используется). Принимающая сторона читает ровно Body Len + 4 (контрольная сумма) байт.

### Body

Используется для хранения данных запроса. Зависит от Command. В случае использования сжатия, должен в первую очередь произвести обратное преобразование согласно алгоритму после проверки контрольной суммы.

### CheckSum

Используется для проверки Headers и Body на целостность. Используемый алгоритм - Castagnoli (CRC-32C). Если Body сжато, проверяется до обратного преобразования согласно алгоритму сжатия.

### Алгоритм рукопожатия

Клиент, решивший установить соединение клиента с сервером, в первую очередь установить соединение с сервером, должен произвести процедуру рукопожатия.

#### Поднятие соединения

См. [Алгоритм установления соединение](#алгоритм-установления-соединения)

#### Отправка Handshake запроса

Клиент отправляет Handshake-запрос, содержащий следующие заголовки (Headers):

- `Command` - 0
- `RequestID` - 0
- `Compression` - 0
- `Body Len` - зависит от реальной длины Body

В Body клиент передает данные согласно следующему формату:

```text
| Login Len (4 bytes) | Login | Hash (32 bytes) | Supported Compressions Len (1 byte) | Compression 1 | Compression 2 | ... | Compression N |
```

Где:

- `Login Len` - длина логина для подключения.
- `Login` - логин для подключения. Представляет собой строку в UTF-8 формате.
- `Hash` - хэш от пароля для подключения. В качестве хэш функции используется Argon2id.
- `Supported Compressions Len` - кол-во поддерживаемых методов сжатия (см. [Сжатие](#сжатие)). Принимает значения от 0 до 255.
- `Compression N` - поддерживаемые клиентом алгоритмы сжатия.

**Примечание автора**: сервер может поддерживать анонимные соединения. В таком случае Login Len становится равным 0, а Hash заполнятеся нулевыми байтами.

Пример Handshake-запроса c поддерживаемыми протоколами Zstd и Lz4:

```text
Hex-версия:

0A DB 01 00 00 00 00 00 00 00 00 00 03 02 01 02 63 8F 96 50

Расшифровка:
	Version: 1
	Command: Handshake
	Request ID: 0
	Compression: -
	Supported compression algorythms: Zstd, Lz4
	CheckSum: 63 8F 96 50
```

#### Ответ сервера

Сервер получив запрос, валидирует его и парсит. 

Возможны 2 сценария:

1. Правильный запроc

В таком случае, сервер отправляет Answer запрос, содержащий следующие заголовки (Headers):

- `Command` - 1
- `RequestID` - 0
- `Compression` - 0
- `Body Len` - зависит от реальной длины Body

В Body сервер передает данные согласно следующему формату:

```text
| 01 | Supported Compressions Len | Compression 1 | Compression 2 | ... | Compression N |
```

Где:

- `Supported Compression Len` - кол-во поддерживаемых методов сжатия из списка, предоставленного клиентом. Принимает значения от 0 до 255.
- `Compression N` - поддерживаемые сервером алгоритмы сжатия.

Пример Answer-запроса с поддержкой Zstd:

```text
Hex-версия:

0A DB 01 01 00 00 00 00 00 00 00 00 02 01 01 01 77 66 37 0A

Расшифровка:
	Version: 1
	Command: Answer
	Request ID: 0
	Compression: -
	Result: OK
	Supported compression algorythms: Zstd
	CheckSum: 77 66 37 0A
```

2. Запрос с проблемами

В данном случае сервер отправляет Answer запрос, содержащий следующие заголовки (Headers):

- `Command` - 1
- `RequestID` - 0
- `Compression` - 0
- `Body Len` - зависит от реальной длины Body

В Body клиент передает данные согласно следующему формату:

```text
| 00 | Error Code (2 bytes) | Traceback ID (16 bytes) | Details |
```

Где:

- `Error Code` - код ошибки. Принимает значения от 0 до 65535. Подробности см. в [Ошибках](#ошибки)
- `Traceback ID` - уникальный идентификатор ошибки.
- `Details` - детальное описание ошибки, зависящее от номера ошибки.

**Примечание автора**: здесь и далее в примерах Traceback ID интерпретируется как бинарный UUID.

Пример Answer-запроса с ошибкой [Unexpected Command](#unexpected-command), вызванной тем, что клиент после Hello-запроса не прислал Handshake-запрос:

```text

Расшифровка:

	Command: Answer
	Request ID: 0
	Compression: -
	Result: NOT OK
	Error: 
		Unexpected Command
		Traceback ID: 6bae3680-7695-4742-92af-0a6fec339825
		Details:
    		Expected Command: Handshake
	CheckSum: 0E 87 11 EA
```

### Алгоритм отправки батча-запросов

#### Отправка Batch-запроса

Клиент отправляет Batch-запрос, содержащий следующие заголовки (Headers):

- `Command` - 5
- `RequestID` - уникальный, т.е. не существует выполняющихся в текущий момент времени запросов с таким же значением
- `Compression` - опционально, поддерживаемый сервером алгоритм
- `Body Len `- зависит от реальной длины Body

В Body клиент передает данные согласно следующему формату:

```text
| Flags (1 byte) | Requests Len (4 bytes) |  Request 1 | Request 2 | ... | Request N |
```

Где:

- `Flags` - флаги настройки выполнения. Подробности см. ниже.
- `Requests Len` - кол-во запросов в батче.
- `Request N` - запрос N. Формат запроса см. ниже.


**Флаги (Flags)**

Представляют из себя уникальные настройки выполнения батча запросов. Биты флагов:

0. `Последовательность выполнения запросов`. 1 - последовательная (по порядку Request Number). 0 - параллельная.
1. `Прерывание при ошибке`. 1 - прерывание дальнейшего выполнения (вернется ошибка [Request Interrupted](#request-interrupted) для оставшихся невыполненных запросов). 0 - возврат ошибки, остальные операции не прерываются.
2. `Возврат результата`. 1 - единоразовый возврат результата всех запросов. 0 - возврат результатов в порядке выполнения (не обязательно в порядке Request Number, если флаг "последовательность выполнения запросов" установлен в 0).
3. Резерв.
4. Резерв.
5. Резерв.
6. Резерв.
7. Резерв.

**Request**

Один из запросов, сформированный в батч. Формат записи:

```text
| Request Number (4 bytes) | Command (1 byte) | Request Body Len (4 bytes) | Request Body |
```

Где:

- `Request Number` - уникальный номер операции в рамках текущего батча.
- `Command` - только операция Read, Delete или Write.
- `Request Body Len` - размер тела запроса
- `Request Body` - Body, формат которого определен для Read-, Delete- и Write-запросов.

Пример Batch-запроса c 2-мя операциями:
- Read-запроса с Request Number = 1 и Key = "key"
- Write-запрос с Request Number = 2, Key = "another-key" и Value="data"

Использованы следующие флаги:
- единоразовый возврат ответа.
- пропуск операции при ошибке.
- операции выполнять последовательно.

Headers:
- `RequestID` = 1
- `Compression` = 0

```text
Hex-версия:

0A DB 01 05 00 00 00 01 00 00 00 00 32 05 00 00 00 02 00 00 00 01 02 00 00 00 03 6B 65 79 00 00 00 02 03 00 00 00 18 00 00 00 0B 61 6E 6F 74 68 65 72 2D 6B 65 79 06 00 00 00 04 64 61 74 61 0B 5B F9 A9

Расшифровка:
	Version: 1
	Command: Batch
	Request ID: 1
	Compression: -
	Flags:
		One answer
		Continue with errors
		Execute sequentially
	Requests:
		1:
			Command: Read
			Key: key
		2:
			Command: Write
			Key: another-key
			Data:
				Type: string
				Value: data
	CheckSum: 0B 5B F9 A9
```

#### Ответ сервера

Сервер получив запрос, валидирует его и парсит. 

Возможны 2 сценария:

1. Правильный запроc. Батч принят на обработку.

В таком случае, сервер отправляет Answer запрос, содержащий следующие заголовки (Headers):

- `Command` - 1
- `RequestID` - тот же, что и у Batch-запроса
- `Compression` - опционально, поддерживаемый клиентом алгоритм
- `Body Len` - зависит от реальной длины Body

```text
| 01 | Results Len (4 bytes) | Result 1 | Result 2 | ... | Result N |
```

Где:

- `Results Len` - кол-во ответов в кадре.
- `Result N` - результат выполнения запроса N. Формат смотри ниже.

**Result**

Один из результатов запроса из батча. Формат записи:

```text
| Request Number (4 bytes) | Result Body Len (4 bytes) | Result Body |
```

Где:

 - `Request Number` - уникальный номер операции в батче.
 - `Result Body Len` - длина Result Body.
 - `Result Body` - Body, который определён для успешных и неуспешных ответов на Read-, Delete- и Write-запросов (см. [Алгоритм чтения данных](#алгоритм-чтения-данных), [Алгоритм записи данных](#алгоритм-записи-данных), [Алгоритм удаления данных](#алгоритм-удаления-данных)).

**Примечание автора**: в случае, если флаг "Возврат результата" установлен в 1, то Answer-запрос будет ровно один. В противном случае, сервер может "возвращать результаты" по одному, используя ту же структуру, или несколькими последовательностями. Клиент обязан сам следить за кол-ом полученных результатов через общее кол-во Requests Len, отправленное клиентом, и кол-вом Results Len, отправленное сервером. Сервер обязан дать ответ на все запросы в батче.

### Таймауты и heartbeat

Протокол не фиксирует интервал проверки сетевой доступности с помощью команды [Ping](#алгоритм-проверки-сетевой-доступности) и таймаут ожидания.

Рекомендации:
- Для сервера:
	- Отправлять Ping каждые 30 секунд, если от клиента не было запросов.
	- Разрывать соединение, если клиент не подал признаки активности: ответ на Ping-запрос или иной запрос в течение 100 секунд после отправки первого Ping-запроса.
- Для клиента:
	- В случае простоя отправлять серверу Ping-запросы каждые 15с.

### Переподключение

При разрыве соединения клиент может переподключиться. Все незавершённые запросы на момент разрыва считаются проваленными, ответа на них не будет. Клиент сам решает, повторить ли запрос.

### Шифрование

Настоящий протокол не фиксирует конкретное шифрование и оставляет конкретную реализацию на усмотрение пользователей настоящего протокола.

Если сервер использует шифрование, клиент обязан подготовить защищенное соединение до отправки Hello-запроса.

В настоящем протоколе рекомендуется использовать TLS для обеспечения безопасности подключения.

### Ограничения

В настоящем протоколе, для полей кадра, для которых не оговорены ограничения, сервер имеет право накладывать свои ограничения на уровне приложений.

Текущие ограничения протокола:

- `Body Len`: 0..4294967295.
- `RequestID`: 1..4294967295 (0 зарезервирован).
- `Version`: 0..255.
- `Requests Len`: 0..4294967295.
- `Results Len`: 0..4294967295.
- `Supported Compressions Len`: 0..255.
- `Supported Versions Len`: 0..255.
- `Error Code`: 0..65535.
- `Current Body Size Limit`: 0..4294967295.
- `Current Batch Size Limit`: 0..4294967295.
